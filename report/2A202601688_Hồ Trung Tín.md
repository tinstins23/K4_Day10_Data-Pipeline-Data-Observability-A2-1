## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết

Cần chứng minh bằng artifact rằng dữ liệu sạch đạt tiêu chuẩn trước khi đưa vào RAG, đồng thời tạo baseline có thể so sánh khi dữ liệu bị corrupt/repair ở Pha 2. Nếu chỉ nhìn metric agent mà không có quality/freshness, khó tách lỗi data khỏi lỗi model.

### Cách triển khai

- **Quality checks:** kiểm tra row count > 0; `paper_id` not null và unique; `title` not null; độ dài `summary` ≥ 40; `age_days` không vượt `freshness_threshold_days` (180). Mọi check ghi pass/fail + expected/actual vào JSON.
- **Freshness:** lấy latest/oldest `published`, đếm `stale_rows`, tính `is_fresh`.
- **Reporting:** render Markdown từ dict metrics/quality/freshness, không hard-code số liệu.
- **Phase 1 orchestration:** raw → clean → Chroma index → test set → evaluate → quality/freshness → report → (optional) agent demo; demo lỗi không chặn artifact baseline.

### Input, output và contract

| Thành phần              | Mô tả                                                                                                             |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Input                   | Cleaned DataFrame (`paper_id`, `title`, `summary`, `published`, `age_days`, …); metrics summary từ evaluation     |
| Output                  | `*_quality.json`, `freshness_report.json`, `phase1_report.md`; Phase 1 còn sinh raw/clean/embeddings/eval/results |
| Module phụ thuộc        | `core.config`, `ingestion.*`, `retrieval.index`, `evaluation.*`                                                   |
| Module sử dụng output   | `phase1.py`; Pha 2 (`corruption_flow`) dùng quality/reporting để so sánh                                          |
| Điều kiện lỗi cần xử lý | Clean rỗng → dừng; agent demo lỗi API → ghi lỗi vào `agent_demo_answers.json`, vẫn giữ baseline                   |

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Cần tách tín hiệu “data có vấn đề” khỏi “agent trả lời kém”.
- **Các phương án đã cân nhắc:** (1) Chỉ dựa vào retrieval/judge metrics; (2) Thêm quality checks + freshness report độc lập trên clean DataFrame.
- **Phương án đã chọn:** Phương án (2).
- **Lý do:** Metric agent phụ thuộc LLM/retrieval; quality/freshness đọc trực tiếp schema dữ liệu nên dễ truy vết nguyên nhân khi corrupt (blank summary, duplicate, stale date…).
- **Bằng chứng quyết định phù hợp:** Baseline quality `success=true`, freshness `is_fresh=true`, `failed_checks=[]` trong `data/quality/`.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:** Agent demo ghi `Agent demo skipped` do Gemini `429 RESOURCE_EXHAUSTED` (quota free tier).
- **Lệnh hoặc bước tái hiện:** `python script/run_phase1.py` → bước demo agent.
- **Nguyên nhân gốc:** Demo gọi LLM provider; vượt quota/request limit, không phải lỗi quality/pipeline.
- **Cách xử lý:** Bọc demo trong try/except; lỗi chỉ ghi vào `data/results/agent_demo_answers.json`, không rollback các artifact baseline đã tạo.
- **Cách xác minh sau khi sửa:** Pipeline vẫn exit thành công; `baseline_metrics.json`, quality/freshness/report vẫn có.
- **Điều học được:** Observability artifact phải tách khỏi bước phụ thuộc LLM không ổn định; baseline reproducibility ưu tiên hơn demo tương tác.

## 7. Hiểu biết về luồng end-to-end

**Câu trả lời:**

1. Crossref API (hoặc snapshot `data/raw/`) → parse `PaperRecord` → cleaning tạo schema sạch + `text_for_embedding`/`age_days` → MiniLM embed → lưu Chroma (`papers-baseline`) và manifest `data/embeddings/`.
2. Test set có `question`, `ground_truth`, `ground_truth_doc_ids`. Retrieval hit khi top-k trả về ID nằm trong ground-truth IDs; answer quality đo bằng token F1 và judge score so với `ground_truth`.
3. Quality checks đánh giá tính đầy đủ/hợp lệ/duy nhất của bản ghi (null, duplicate, độ dài summary…). Freshness chỉ quan tâm độ cũ theo `age_days`/`published` so với ngưỡng 180 ngày.
4. Cùng test set giúp so sánh công bằng: thay đổi metric phản ánh data/index, không phải do đổi bộ câu hỏi.
5. Repair thành công khi rebuild từ raw cho ra quality/freshness gần baseline và agent metrics phục hồi so với trạng thái corrupted (artifact: repaired clean/metrics/quality + `corruption_report.md`). _Pha 2 trên máy này chưa có đủ artifact corrupted/repaired tại thời điểm viết báo cáo._

### Kết luận từ số liệu

1. [Baseline clean data] → [quality pass + freshness fresh] → [retrieval_hit_rate=1.0, judge_accuracy≈0.96].
2. [Repair action] → [chưa chạy trên máy này] → [chưa có số liệu phục hồi để kết luận].

Corruption nào ảnh hưởng rõ nhất và vì sao?

Chưa đo được trên artifact thực tế. Kỳ vọng: blank/noise summary và duplicate `paper_id` ảnh hưởng rõ tới quality + retrieval/answer; làm cũ `published` ảnh hưởng rõ tới freshness.

Kết quả nào khác với kỳ vọng ban đầu?

Agent demo không chạy được do quota Gemini, nhưng evaluation baseline vẫn có metrics hợp lệ — cho thấy tách demo khỏi eval/quality là đúng.

## 9. Điều học được và hướng cải thiện

### Ba điều quan trọng nhất

1. Pipeline cần raw snapshot để tái lập và repair, không chỉ “fetch một lần rồi quên”.
2. Quality và freshness là tín hiệu sớm, độc lập với LLM, giúp phát hiện data drift/corruption trước khi user nhận câu trả lời sai.
3. RAG agent chỉ tốt khi data sạch và index đúng; observability giúp chứng minh mối quan hệ data → metric bằng artifact.

### Nếu có thêm thời gian

Chạy đủ Pha 2 và điền bảng baseline/corrupted/repaired bằng số liệu thật; thêm check `text_for_embedding` not blank vào quality suite và đo xem corruption dạng truncate/noise có bị bắt sớm hơn không.
